A position in a path file only means something once you know where zero is and which way the axes point. That
choice is the **field frame**, and [FieldFrame](/reference/core/fieldframe/) converts between frames.

<FieldFrames />

## The frame

Myelin uses the WPILib 2027 field frame. Paths, field.json obstacles and named points are all stored in it.

| Thing | Where it is |
| --- | --- |
| Origin | The center of the field |
| +X | Toward the blue alliance wall. Blue's half is `x > 0`. |
| +Y | To the left when you face +X |
| Headings | Counterclockwise from +X. Radians in code, degrees in files. |

## What it does

Paths are drawn for blue. On red, each loop the follower does this:

1. It converts the measured pose and velocity into the blue frame with `toBlue`.
2. It follows the blue path exactly as it would on blue.
3. It converts the commanded velocity back with `fromBlue` and sends that to the drivetrain.

Nothing is rebuilt. A half turn or a mirror keeps every length, so the blue
[speed plan](/concepts/speed-plan/) is the red plan.

## Pick the red value

| Value | Use it for | Meaning |
| --- | --- | --- |
| `BLUE` | The blue alliance | No change |
| `RED_HALF_TURN` | Red, on a field with rotational symmetry | The field turned 180 degrees about its center |
| `RED_MIRROR` | Red, on a field with mirror symmetry | The field mirrored across the line `x = 0` |

```java
// BLUE on blue, the value you pass in on red
FieldFrame frame = Conversions.allianceFrame(FieldFrame.RED_HALF_TURN);
```

Read the alliance when the path starts, not when the auto is built. An unknown alliance counts as blue.

## The numbers

| | `RED_HALF_TURN` | `RED_MIRROR` |
| --- | --- | --- |
| Position `(x, y)` | `(-x, -y)` | `(-x, y)` |
| Heading `θ` | `θ + π` | `π - θ` |
| Velocity `(vx, vy)` | `(-vx, -vy)` | `(-vx, vy)` |
| Spin `ω` | `ω` | `-ω` |

- Headings are wrapped to the range from -π to π.
- Each transform is its own inverse, so `toBlue` and `fromBlue` do the same arithmetic.
- A mirror flips the sign of the curvature. `FieldFrame.mirrors()` is true for `RED_MIRROR`.
- In the library's tests, a path built from flipped inputs agrees with the transformed blue plan to 1e-8 m, and
  a simulated robot driven both ways on red agrees to 1e-6 m.

## Older files

Until 2026-11-26 the frame had +X toward the red wall, so blue was at `x < 0`. An older file is turned half a
turn when it is read:

```text
(x, y, heading)  becomes  (-x, -y, heading + 180 degrees)
```

| File | Already in the 2027 frame | Turned when read |
| --- | --- | --- |
| `*.path.json` | `"schema": 4` | Schema 1 to 3 |
| `field.json` | `"schema": 2` | No `schema` key |
| `.pathproject.json` named points | `"schema": 2` | Schema 1 |

In a path file the turn covers every waypoint position, `tangentDegrees`, `headingDegrees`, rotation target
`degrees` and face-point zone point. You do not edit an old file by hand. The editor writes it as schema 4 on the
next save. See the [path file](/files/path-file/).

## WPILib alpha-7 and alpha-8

:::caution
WPILib 2027.0.0-alpha-7 and alpha-8 still report poses with the old origin at a corner of the field. Robot code
must convert everything that crosses between WPILib and the library.
:::

With `L` the field's length and `W` its width in meters:

| What | Direction | Conversion |
| --- | --- | --- |
| Poses: the measured pose, moving goals | Into the library | `(L/2 - x, W/2 - y, heading + 180 degrees)` |
| Velocities | Into the library and back out | `(-vx, -vy, ω)` |

If a first run does not follow its path, check this before anything else.

## What it does not do

- **It does not read the alliance.** `Conversions.allianceFrame` in the WPILib layer asks the driver station.
- **It does not pick the symmetry.** You pass `RED_HALF_TURN` or `RED_MIRROR`.
- **It does not move obstacles.** field.json describes the field as it physically is, for both alliances.
- **It does not flip real-world goals.** A pose from vision is taken as given. Only goals authored for blue are
  flipped.
