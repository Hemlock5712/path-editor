The library never touches a motor. It asks your drivetrain for three things each loop and hands back a velocity.

## Hand over three things

| The library needs | Type | Meaning |
| --- | --- | --- |
| The pose | `Supplier<Pose2d>` | Where the robot is on the field, and which way it faces. Your fused estimate, vision included. |
| The field velocity | `Supplier<ChassisVelocities>` | How fast the robot is moving, **field-relative**: `vx` and `vy` along the field's axes, `omega` in rad/s. |
| A way to drive | `Consumer<ChassisVelocities>` | Takes a field-relative velocity and makes the robot drive at it. |

The drivetrain must also be a Commands v3 `Mechanism`, so the library's commands can require it.

```java
// Once, in robot init. Every command otf makes uses these.
Pathfinding otf = new Pathfinding(
    paths,                                           // the PathLibrary
    FollowerConfig.defaults(paths.robot()),          // the follower's settings
    () -> drive.getPose(),                           // 1. the pose
    () -> drive.getFieldVelocity(),                  // 2. the field velocity
    velocity -> drive.driveFieldVelocity(velocity),  // 3. a way to drive
    FieldFrame.RED_HALF_TURN);                       // how a blue path becomes a red one
```

`getPose`, `getFieldVelocity` and `driveFieldVelocity` are your methods, not the library's.

## Write them on a CTRE swerve drivetrain

These are the team's. `drivetrain` is the class Tuner X generates.

```java
// Field-relative closed-loop velocity. Closed-loop, so slow final moves still happen.
private final SwerveRequest.ApplyFieldVelocity fieldVelocityRequest =
    new SwerveRequest.ApplyFieldVelocity()
        // Fixed to blue. The library's output must not be turned round on red a second time.
        .withForwardPerspective(SwerveRequest.ForwardPerspectiveValue.BlueAlliance)
        .withDriveRequestType(DriveRequestType.Velocity);

public Pose2d getPose() {
  return drivetrain.getState().Pose;
}

public ChassisVelocities getFieldVelocity() {
  var state = drivetrain.getState();
  // The drivetrain measures speed relative to the robot. Rotate it by the heading to get field directions.
  return state.Velocity.toFieldRelative(state.Pose.getRotation());
}

public void driveFieldVelocity(ChassisVelocities fieldVelocity) {
  drivetrain.setControl(fieldVelocityRequest.withVelocity(fieldVelocity));
}
```

## The field frame

The library works in the **WPILib 2027 field frame**: the origin is the center of the field, +X points at the
blue alliance wall, and +Y is to the left when you face that wall. WPILib 2027 alpha-7 and alpha-8 still put the
origin at the blue corner with +X toward the red wall.

<FieldFrames />

:::danger[Convert all of it, or none of it]
On alpha-7 or alpha-8, convert every value that crosses between your robot and the library: the pose in, the
velocity in, the velocity out, every goal, and the wheel forces if you send them. Converting the pose alone
drives the robot away from the path.
:::

| Crossing | Conversion |
| --- | --- |
| A pose, either direction | `(L/2 - x, W/2 - y, heading + 180°)` |
| A field velocity, either direction | `(-vx, -vy, omega)` |
| Wheel forces, field-relative | each one negated |

`L` and `W` are the field's length and width. One helper does both directions.

```java
public final class CenterFrame {
  /** A pose in the other frame: the same spot, the same way round. */
  public static Pose2d convert(Pose2d pose) {
    return new Pose2d(
        FIELD_LENGTH / 2.0 - pose.getX(),
        FIELD_WIDTH / 2.0 - pose.getY(),
        pose.getRotation().plus(Rotation2d.PI));
  }

  /** A field-relative velocity in the other frame: x and y point the other way, the spin is the same. */
  public static ChassisVelocities convert(ChassisVelocities fieldVelocity) {
    return new ChassisVelocities(-fieldVelocity.vx, -fieldVelocity.vy, fieldVelocity.omega);
  }
}
```

Convert in one place, the wiring.

```java
Pathfinding otf = new Pathfinding(
    paths,
    FollowerConfig.defaults(paths.robot()),
    () -> CenterFrame.convert(drive.getPose()),                           // pose in
    () -> CenterFrame.convert(drive.getFieldVelocity()),                  // velocity in
    velocity -> drive.driveFieldVelocity(CenterFrame.convert(velocity)),  // velocity out
    FieldFrame.RED_HALF_TURN);
```

Goals you pass in need it too: `otf.to(drive, CenterFrame.convert(goal))`. When WPILib moves its origin to the center, delete the helper. [The field frame](/concepts/field-frame/) has the
background.

## Check it before driving a path

A wrong sign here looks like a broken follower later. Check the three methods in your robot's own frame first.

1. Put the robot on the field, facing the red wall on alpha-7, and drive it by hand toward the red wall. The pose's
   `x` should grow and `getFieldVelocity().vx` should be positive.
2. Slide it to its left. `y` should grow and `vy` should be positive.
3. Turn it counterclockwise seen from above. The heading should grow and `omega` should be positive.
4. Call `driveFieldVelocity(new ChassisVelocities(0.5, 0, 0))` from a test command. The robot should move toward
   the red wall at half a meter per second whichever way it is facing, and on either alliance.
